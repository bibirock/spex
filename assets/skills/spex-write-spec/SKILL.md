# Spex: Write Spec — 清楚且可驗收的需求

## 載入與前置

- 本階段處理 WHAT／WHY；技術設計由 `spex-plan`，實作層拆解由 `spex-task`。
- 讀取 [spec-template](../../reference/spex/spec-template.md)，使用其必填章節與品質檢核清單作為產出契約。
- 讀取 `.claude/rules/sdd-workflow.md` 的「核心原則」「Tracker Adapter」，遵守已授權產品範圍。
- 補強既有卡片時，依 [Adapter 規範](../../reference/adapters/README.md#skills-引用-adapter-規範) 讀 `TRACKER.readItem` 及必要附件操作。
- 讀現有 description／AC、相關決策、程式碼入口與實際附件，不要求使用者重述已知資訊。
- 既有 spec／流程歷史保留原位置；只修改授權補強的規格，不重設其他 Story 範圍。

## 1. 判斷已知資訊與必要問題

| 情況 | 動作 |
|---|---|
| 規格、附件、程式碼或使用者決策已說明 | 直接納入，標明來源 |
| 可合理判斷且不改變產品範圍 | 採用並簡述假設 |
| 答案改變 In／Out Scope、AC、權限或重要行為且無法判斷 | 提出具體問題 |
| 與本需求無關或只屬技術偏好 | 不問，留適當階段處理 |

問題須同時具備相關性、可回答性與未被既有資訊涵蓋；不湊題數，也不省略真正會改變需求的問題。
先完成資訊已足夠的部分，將未決項集中呈現；已授權內容不逐段要求再次確認。
review 或實作發現的新功能建議只列待確認，不把它悄悄寫成既定需求。

## 2. 角色與完整旅程

釐清使用者是誰、想達成什麼、開始前需要哪些身分／資料／狀態。
寫出從進入功能、操作、等待、成功到下一步的完整可觀察路徑。
明列 In Scope 與非空的 Out of Scope；範圍外項目須貼近本需求，避免泛泛列清單。
補上失敗後的可見結果、是否能重試、如何回復或保留已輸入資料。
既有產品行為將被替代或移除時明記決策，讓 Plan 能判定舊測試的保留或汰換。

## 3. 邊界探索

| 維度 | 要決定的行為 |
|---|---|
| 空值／缺漏 | 未輸入、空資料、必填欄位缺少時的結果 |
| 格式 | 格式、編碼、非法值、錯誤訊息 |
| 上限／規模 | 長度、大小、數量、併發與超限結果 |
| 錯誤路徑 | 外部失敗、網路中斷、逾時、重試與回復 |
| 權限／角色 | 可見內容、允許操作、跨租戶／匿名邊界 |
| 狀態切換 | 重複操作、切頁、舊快取、處理中或完成後再操作 |

各維度有交代或明示不適用，不憑空增加不需要的能力。
涉及既有認證、檔案處理或部署流程時，保留 repository `AGENTS.md` 與 `.claude/rules/testing.md` 規定的環境邊界，不以本機替身取代真實帳戶要求。

## 4. 列舉完整性

需求出現「一組格式／設定／頁面／provider 都要」時，列出全部實際成員與是否在範圍內。
成員存在於 codebase 時用 `rg` 等工具取得實際清單；只詢問無法由既有授權判定的成員。
不以一個代表案例代替全部成員；並列條件各自有預期結果。
沒有成組項目時依範本填「不適用」，不為填表創造需求。

## 5. 撰寫可二元判定的 AC

使用穩定的 AC 編號及 Given／When／Then；每條寫明前置、動作與可觀察的結果。
避免「快速」「正常」「易用」等無判準文字；有數值或格式要求時寫清單位與邊界。
AC 應能對應有意義的測試、指令或可觀察證據，不能只要求程式碼存在。
UI AC 應驗證可見結果、互動狀態、API 邊界與 console error/warning，交付時使用 `.claude/rules/testing.md` 指定的 E2E／UI 驗證工具。
涉及檔案處理或多階段流程的成功需求，驗收場景須以實體 fixture 走完整條使用者鏈到最終可觀察結果。
格式拒絕、超限等未產生後續產物的失敗場景，不虛構後續成功步驟。
缺陷規格另附最小重現步驟、影響範圍、預期與實際差異、修復完成定義。
視覺需求附可檢視參考及可辨認的驗收條件，不能只寫「美觀」。

## 6. 決定 Story 與 Epic

依使用者價值與可獨立驗收的切片判斷，不因 AC 數量或檔案數強制拆分。
不同角色、主要路徑或可獨立交付的目標，且拆開仍有價值時，可拆為多張 Story。
單一目標僅跨多個技術層時可維持同一 Story，不按技術層拆成無法展示的需求。
較大需求以父 Epic 記錄整體目標、跨 Story AC、共同邊界及依賴，每張 Story 仍有完整範本。
保留每條原始需求的歸屬，不能因拆卡省掉邊界或列舉成員；也不為卡片數上限砍範圍。

Epic 內 Story 先完成各自 focused TDD 與相關回歸，記錄 Implement 完成待 Epic 驗收。
全部納入 Story 實作後才集中一次 review、完整機器驗證與一次獨立 verifier。
無 Epic 的單卡以自身為驗收單位；規格拆分不意味著逐 Story 重做完整驗收。

## 7. 估點與品質檢查

依範本使用 Fibonacci `1 / 2 / 3 / 5 / 8 / 13 / 20`，只衡量 MVP 實作複雜度。
說明實作面、狀態與契約、整合面、驗證工作量；排除優先級、失敗成本與商業風險。
Story 依範本不超過 13，20 用於 rollup；估點過大時重看可交付切片，保留完整需求。
估點只供規劃，不是驗收 PASS／FAIL 或固定時間停工的依據。

交付前核對範本必填章節、二元 AC、邊界、列舉、驗收場景、估點與缺陷附加資訊。
每個 In Scope 項都有 AC 或可驗證場景，Out of Scope 清楚，未決問題與假設可辨識。
檢查拆分樹沒有漏項、重複責任或互相矛盾的依賴。

## 8. 交付與下一步

產出完整 Story 規格；有 Epic 時一併給父級摘要、每張 Story 全文、依賴與需求歸屬。
預設交付可貼入 tracker description 的文字；使用者已要求寫入或建卡時直接在授權範圍內落地。
建卡先讀目前 adapter 的「規格建卡欄位對照」，使用支援的操作、正確格式、父子關聯與估點欄位。
adapter 不支援建頂層卡時交付完整規格與可用替代，不臆造工具或假稱已建卡。
如需流程紀錄，使用 `TRACKER.addComment` 追加「`## [Spex] Spec 完成`」，不覆寫舊紀錄。

完整單卡交 `spex-plan`；已授權多卡執行交 `spex-schedule`，可依既有授權直接續行。
規格和執行授權不自動包含 master merge／push，該操作須有明確人工授權。
