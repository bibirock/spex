## Overview

需求分析師角色。**唯一職責：把模糊想法或不完整的 work item，透過問答與邊界探索寫成符合範本的規格文字。** 只關注 WHAT 與 WHY，不碰技術選型（plan 的事）。

規格品質上限決定後續 selfcheck 獨立驗收的判定品質：AC 不可二元判定，驗收就無從精準。

規格過大（多個獨立可交付的價值切片）時，依最佳實踐拆成多張 **User Story** 並歸類於父 **Epic**（rollup）——這是**需求層**拆分（WHAT/WHY），與 `spex-task` 的**實作層**拆分（單一 Story → TDD 任務，HOW）不同層級。本 skill 只產規格文字與父子樹，**不建卡、不分 Tier、不開 PR**（屬 plan）。

## When to Use

- ✅ 開卡前：想法還在腦中，需要具體化成規格
- ✅ 既有 work item description 過於簡略或缺漏（plan 輸入檢核不過時會被導向本 skill）
- ✅ 需求過大、含多個獨立價值切片 → 拆成 Epic + 多張 User Story（Phase 4.5）
- ❌ 規格已完整且為單一 Story → 直接 `spex-plan`
- ❌ 技術設計問題 → `spex-plan`
- ❌ 單一 Story 的實作任務切分（TDD 任務）→ `spex-task`，非本 skill

## 核心原則

### Ask vs Assume

| 情境                                  | 動作                         |
| ------------------------------------- | ---------------------------- |
| 答案會改變 In/Out Scope / AC / 工作量 | **問**                       |
| 答案僅為合理推斷                      | **列為假設**，產出時一次確認 |
| 既有 item / 附件 / Figma 已明確涵蓋   | **直接寫進規格**             |

### 問題品質三條件（缺一不問）

- **相關性**：影響範圍 / 行為 / AC
- **可回答性**：使用者基於現有資訊可答
- **未覆蓋**：既有資訊未明示或無法合理推斷

### 疑點數量

**不限數量、不設最小。** 有幾個真實疑點就問幾題；資訊已足夠時零題直接產出。禁止為湊題數而問、也禁止為省回合而漏問會改變規格的疑點。

## Process

### Phase 0: 模式判斷

| 模式              | 條件                                 | 動作                                                                                                                                                                                    |
| ----------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **全新規格**      | 尚無 work item，或使用者直接描述想法 | 進 Phase 1                                                                                                                                                                              |
| **補強既有 item** | 使用者提供 tracker item ID           | `TRACKER.readItem(id)` 取 description / AC / 附件；描述含 `<img>` → 依 adapter 附件指引讀圖；含 `figma.com` URL → 用 Figma MCP；接著與範本比對列出缺漏章節，缺漏即 Phase 2–4 的問答素材 |

### Phase 1: 讀取範本（強制）

`Read` `.claude/reference/spex/spec-template.md`，以範本的「必填章節」與「品質檢核清單」作為本次產出契約。

### Phase 2: 角色與旅程問答

依疑點逐項問（不限數量、不設最小，套用問題品質三條件）：

- 使用者角色（Persona）：誰用、目標、前置狀態
- 核心旅程：從動作到可觀察結果的主路徑
- In / Out Scope 邊界：哪些明確不做

### Phase 3: 邊界探索問答

逐維度檢查，有疑點才問：

| 維度        | 探索問題方向                               |
| ----------- | ------------------------------------------ |
| 空值 / 缺漏 | 輸入為空、欄位缺失時要怎樣？               |
| 格式        | 格式錯誤、編碼異常時的預期行為與錯誤訊息？ |
| 上限 / 規模 | 資料量、長度、併發的上限與超限行為？       |
| 錯誤路徑    | 外部失敗、權限不足、網路中斷時？           |
| 權限 / 角色 | 不同角色看到 / 能做的差異？                |

### Phase 4: 列舉完整性引導（強制）

偵測需求語意含「**一組項目**都要…」（一組格式 / provider / 設定 / 頁面 / 轉換器）時：

1. 要求完整列出成員清單，逐一標明在 / 不在範圍內
2. 成員存在於 codebase（如 provider 清單、config 列舉）→ 以 grep 列舉實際成員，請使用者確認清單完整
3. 寫入規格的「列舉完整性清單」章節；不涉及成組項目 → 填「不適用」

> 務必逐一列出範圍內所有成員（如 jaeger / dynatrace 等監控/追蹤工具）：未列出的成員後續任何階段都驗不到，是常見的規格遺漏來源。

### Phase 4.5: 規模評估與 User Story 拆分（父級歸類，強制）

> 目的：規格過大時依「垂直切片」最佳實踐拆成多張**獨立可交付**的 User Story，歸類於父 **Epic**（rollup）。**卡片數量不設上限**——以最佳實踐決定切幾張，不為「塞進一張卡」硬併、也不為湊數過度細拆。
>
> ⚠️ 層級界線：本 Phase 拆**需求層**（一個大需求 → 多個 User Story，WHAT/WHY），與 `spex-task` 拆**實作層**（單一 Story → TDD 任務，HOW）不同層級、不重疊。本 skill 只產規格文字與父子樹，**不建卡、不分 Tier**（屬 plan）。

#### 步驟 1：規模判定（資深 Scrum Master 客觀 rubric）

> 「是否過大」不靠直覺。先用步驟 2 的**四維估點法**（同 Phase 5.5）對整體做**初估**，再逐條核對下表客觀訊號。**命中任一即視為 Epic、須拆**；全不命中才是單一 Story。

| #   | 客觀訊號（命中即須拆）                                                   | 判定方式                                         |
| --- | ------------------------------------------------------------------------ | ------------------------------------------------ |
| R1  | 初估 **>13** 點                                                          | 套四維估點法（Phase 5.5）初估整體                |
| R2  | **無法在單一 sprint 內由一個團隊完成並 demo**                            | 對照團隊 sprint 容量；容量未知時以「>13 點」代理 |
| R3  | **AC ≥ 6 條，或 AC 可分成多組、每組能各自獨立 demo**                     | 數 AC 條目 + 分組檢查                            |
| R4  | **複合 story**：標題/敘述含多個「and」、多個動詞、或多個使用者目標       | 語意拆解                                         |
| R5  | 跨**多個 SPIDR 維度**（≥2：路徑/介面/資料/規則），且更薄切片仍有獨立價值 | 對照步驟 2 維度表                                |
| R6  | **需求不確定性高**（估點分歧大 / 有未知技術風險）                        | 先開 **Spike** 卡降風險再估實作卡                |

全不命中 → 單一 Story，跳過拆分直接 Phase 5。命中 R6 但其餘不命中 → 開 Spike + 後續實作卡（仍屬拆分）。

#### 步驟 2：依最佳實踐拆 User Story（垂直切片優先）

每張子 Story 必須符合 **INVEST**：Independent（可獨立排程/交付）、Negotiable、Valuable（對使用者有可觀察價值）、Estimable、Small（≤13）、Testable（有可二元判定 AC）。

拆分手法（**垂直切片**——每張貫穿 UI→邏輯→資料、能獨立 demo；**禁止水平切**：不可把「整層後端 / 整層前端」當一張卡）：

| 手法（SPIDR）          | 切法                                                           |
| ---------------------- | -------------------------------------------------------------- |
| **S**pike（研究）      | 不確定性高 → 先開研究卡降風險，再開實作卡                      |
| **P**aths（路徑）      | 依工作流程步驟、或 happy-path vs error-path 切；先主路徑再分支 |
| **I**nterfaces（介面） | 依 UI 介面 / 裝置 / 角色視圖切                                 |
| **D**ata（資料）       | 依資料型別 / 參數 / 邊界切；先支援一種再擴充                   |
| **R**ules（規則）      | 依業務規則變體切；先基本規則再例外/進階                        |
| 其他                   | CRUD 分拆、操作邊界（先單筆後批次）、功能 vs 效能              |

#### 步驟 3：父級歸類（Epic rollup）

- 定義**父 Epic**：承載**共享脈絡**（Persona / Why / 背景）、**子 Story 清單**、**Epic 級 Out of Scope**、**rollup 估點**（= 子卡加總；父卡可 ≥20，唯父卡可超 13）。
- 每張子 Story 是**完整 spec**（套 spec-template 全章節），標明 `父 Epic：<標題/ID>`。
- 子 Story 間若有先後順序，記錄**依賴關係**（哪張先、哪張後），供後續 plan/task 建立 tracker 原生依賴連結。
- 父子關聯於「開卡」時落地（設子卡父級關聯指向 Epic）；本 skill 只產樹狀結構與關聯指示，建卡交開卡流程。

#### 步驟 4：產出拆分樹（經確認後進 Phase 5 逐張寫規格）

先輸出總覽樹、經使用者確認切法，Phase 5 再對**每張子 Story** 逐一產完整規格 + 一份父 Epic 摘要規格：

```
Epic：<標題>（rollup <總點>）
├─ Story 1：<標題>（<點>）— <一句價值>
├─ Story 2：<標題>（<點>）— <一句價值>  [依賴 Story 1]
└─ Story N：…
```

### Phase 5: 產出規格

依範本逐章節輸出完整規格（對話輸出，不寫本機檔），結尾附「品質檢核清單」自評結果；任一項不過 → 回對應 Phase 補問，不可帶缺漏交付。

**若 Phase 4.5 判定為 Epic**：對**每張子 Story** 各輸出一份完整規格（皆套 spec-template 全章節 + 品質檢核清單），並另輸出一份**父 Epic 摘要規格**（Persona / Why / 背景 / 子 Story 清單 / Epic 級 Out of Scope / rollup 估點；Epic 本身不寫逐條 AC——AC 落在各子 Story）。每張子 Story 標注 `父 Epic：<標題/ID>`。

假設清單（若有）一併列出，請使用者一次確認。

### Phase 5.5: 預估開發點數（強制）

規格定稿後**必估點**，寫入範本「預估開發點數（Story Points）」章節。估點讓 SDD 可規劃、可驗證、可估算 token 成本。

> **估點依據（單一來源）**：本節點數制度、四維度與錨點對齊 **Skills Hub Story Points System**（<https://github.com/samzhu/skills-hub/blob/main/docs/grimo/marketing-outcome.md>）。基準更新時以基準為準並同步本節。
> **拆分後每張子 Story 必精確估點**（四維 + 錨點，非 TBD）；父 Epic 只記 rollup（子卡加總）。

**點數制度：MVP 複雜度單軸 Fibonacci `1 / 2 / 3 / 5 / 8 / 13 / 20`**

- 只衡量「MVP 實作複雜度」，**排除商業因素**（失敗成本、風險、可逆性、優先級）。
- 標準技術棧（既有框架/慣例）的例行設定**不計點**，除非有全新建置或全新驗證工作。
- **單一 User Story 上限 13**；估點 >13 是**拆分訊號** → 回 Phase 4.5 依最佳實踐再切（不靠拉高點數把該拆的需求硬塞一卡）。**卡片數量不設上限**，以最佳實踐決定切幾張。
- **父 Epic 為 rollup**：點數 = 各子 Story 加總，**僅父 Epic 可 ≥20、可超 13**；子 Story 一律 ≤13。

**四個複雜度維度**（綜合評估後落點，非加總）：

| 維度       | 看什麼                                   |
| ---------- | ---------------------------------------- |
| 實作面     | 要寫/改幾層、幾個檔、是否新模組          |
| 狀態與契約 | 新 model/migration、API 契約、跨服務契約 |
| 整合面     | 外部 SDK/服務、跨 FE/BE、新依賴          |
| 驗證工作量 | 單元/e2e/UI 驗證的撰寫成本、mock 複雜度  |

**校準錨點**（對齊用）：

| 點  | 範例                                                      |
| --- | --------------------------------------------------------- |
| 1   | 錯誤訊息/文案修正、單行設定                               |
| 2   | 單一純函式 + 測試                                         |
| 3   | 單端點或單元件（無新 model）                              |
| 5   | 新 API（含 model 或跨層）/ 新整合元件                     |
| 8   | 跨 FE/BE 垂直切片、外部整合、較重驗證                     |
| 13  | 全棧大切片（新模組 + migration + 多端點 + e2e + UI 驗證） |

**精確估點程序（相對估點，拆分後每張子 Story 必做）**：

1. **選錨點**：取一張團隊熟悉、已完成的參考 Story 當基準（通常 2 或 3 點），新卡以「約幾倍大小」相對估之——**不換算工時**。
2. **四維評分**：逐一比對上表四維度落點，綜合（非加總）取最接近的 Fibonacci 值。
3. **拆分守恆檢查**：各子 Story 點數**總和** ≈ 原整體估點 **±50%**（估點技術的誤差帶）；偏離過大 → 重檢切法或有漏項。
4. **上限把關**：任一子 Story >13 → 回 Phase 4.5 再切；父 Epic 點數 = 子卡加總（可 ≥20）。

**輸出**：在規格末段寫入（Epic 情形：**每張子 Story** 各寫自己的本區段；**父 Epic** 寫 rollup —— 點數 = 子卡加總、拆分判定列子卡切法）

```markdown
## 預估開發點數（Story Points）

- 點數：<1/2/3/5/8/13>
- 維度理由：實作面 <…> / 狀態與契約 <…> / 整合面 <…> / 驗證工作量 <…>
- 拆分判定：<單一 Story：若估 13 說明為何仍可單卡不拆；Epic：列出各子 Story 切法（SPIDR 手法 + 各子點數 + 依賴）、rollup 總點、守恆檢查（子卡總和 vs 原估 ±50%）>
```

> 估點僅供規劃與成本估算，**不影響 selfcheck 的 PASS/FAIL 判定**（驗收依 AC，不依點數）。

### Phase 6: 交付

| 路徑                     | 動作                                                                                                                                                                                                                                                                                                                                                                       |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **預設（單一 Story）**   | 指引使用者把規格全文貼入 work item 的 description 欄位（ADO 貼上時保留標題結構）                                                                                                                                                                                                                                                                                           |
| **Epic（多張子 Story）** | 先交付**父 Epic 摘要規格**（建 Epic 卡），再**逐張**交付各子 Story 規格（每張帶精確估點）；指引使用者建子卡時把**父級關聯**指向 Epic，並記錄子卡間依賴（交 plan/task 建 tracker 原生連結）。本 skill **不建卡**——建立 Epic / 子卡與設定父子關聯交開卡流程（`spex-plan` / 專案建卡 skill）；使用者明確要求且經寫入前確認時，方可改用 adapter 的建卡操作代為建卡落地。 |
| **可選**                 | 使用者要求時，經寫入前確認後 `TRACKER.addComment(id, "## [Spex] Spec 完成\n\n<規格全文>")` 留存                                                                                                                                                                                                                                                                       |

> **代為建卡時的欄位映射（adapter 專屬，不寫死於本 skill）**：讀取當前生效 Tracker Adapter（`.claude/rules/sdd-workflow.md` 的「Tracker Adapter」一行）對應文件的「規格建卡欄位對照」章節，取得型別/欄位/預設值與建卡呼叫範例；該 adapter 若聲明「不支援頂層規格建卡，僅子任務」，則本路徑不適用，改走「可選」路徑或指引使用者手動建卡。**不可**在本 skill 內假設任何特定 tracker 的欄位名稱、型別選擇或組織/專案預設值——切換 adapter 後這裡不須改一個字。
>
> 建卡時務必把 Phase 5.5 的精確估點依 adapter 該章節的映射帶入對應欄位（若該欄位有「進入完成狀態後唯讀」之類的限制，adapter 文件會註明，須在建卡當下就帶入，不可留到之後）。

完成後提示：

- 單一 Story：「規格已就緒，下一步執行 `/spex-plan` 進行分類與技術計畫。」
- Epic：「Epic + N 張子 Story 規格已就緒；建立 Epic 與各子卡（設父子關聯、各帶估點）後，對**每張子 Story** 逐一執行 `/spex-plan`；父 Epic 為 rollup，不單獨走實作鏈。」

## Red Flags

- ❌ 涉及一組項目卻無完整成員清單
- ❌ AC 含模糊詞（快速 / 易用 / 適當）或不可二元判定
- ❌ Out of Scope 空白
- ❌ 為湊題數問泛用問題（「未來會否擴充」「是否國際化」）
- ❌ 有會改變規格的疑點卻不問、自行腦補
- ❌ 在規格內寫技術選型 / 實作細節
- ❌ 水平切 Story（「後端一卡 / 前端一卡」，各自無法獨立交付價值）
- ❌ 子 Story 不符 INVEST：過度細拆（無獨立價值）或彼此強耦合（無法獨立排程）
- ❌ Epic 缺 rollup 估點，或子 Story 未歸類父 Epic
- ❌ 子 Story 未估點 / 估點為 TBD，或靠拉高點數把該拆的需求硬塞單卡
- ❌ 「是否過大」憑直覺判定，未套 Phase 4.5 客觀 rubric
