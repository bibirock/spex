# Spec 輸入範本（work item description 標準格式）

> 本範本由 spex 安裝，是 SDD 流程的**規格單一格式來源**：
> `spex-write-spec` 依本範本引導產出規格；`spex-plan` 依本範本檢核輸入完整性；`spex-selfcheck` 以「驗收標準」與「列舉完整性清單」作為獨立驗收的判定依據。
> 規格貼於 tracker work item 的 **description** 欄位（ADO 為 HTML，貼上時保留標題結構）。

---

## 範本結構（必填章節）

```markdown
## 使用者角色（Persona）

- 角色：<誰會使用這個功能；例：外包開發者 / 平台維運 / 終端使用者>
- 目標：<這個角色要達成什麼>
- 前置狀態：<使用前的環境 / 權限 / 資料狀態>

## 背景與動機（Why）

<1–3 句：為什麼要做、解決什麼問題。>

## In Scope

- <本次明確要做的事 1>
- <本次明確要做的事 2>

## Out of Scope

- <明確不做的事；防止功能延伸>

## 驗收標準（AC）

> 每條 AC 必須**二元可判定**（能明確回答通過 / 不通過），含具體格式、數值或行為條件。
> 禁用模糊詞：「快速」「易用」「適當」「正常」「美觀」。

AC-01: <情境名稱>
  Given <前置狀態>
  When <操作>
  Then <可觀察、可驗證的結果（含格式 / 數值條件）>

AC-02: ...

## 邊界條件

| 維度 | 條件 | 預期行為 |
|---|---|---|
| 空值 / 缺漏 | <輸入為空、欄位缺失時> | <預期> |
| 格式 | <格式錯誤、編碼異常、非法字元時> | <預期（含錯誤訊息格式）> |
| 上限 / 規模 | <資料量上限、長度上限、併發> | <預期> |
| 錯誤路徑 | <外部失敗、網路中斷、權限不足> | <預期> |

## 列舉完整性清單

> 需求涉及「**一組項目**都要…」（一組格式 / provider / 設定 / 頁面 / 轉換器）時**必填**：
> 逐一列出全部成員，並標明各成員是否在範圍內。沒有列出的成員視為範圍外。
> 不涉及成組項目時填「不適用」。

| 成員 | 在範圍內？ | 備註 |
|---|---|---|
| <成員 1（例：jaeger）> | ✅ / ❌ | |
| <成員 2（例：dynatrace）> | ✅ / ❌ | |

## 驗收場景

1. <端到端場景：從使用者動作到可觀察結果的完整路徑>
2. <失敗 / 回復場景>

## 預估開發點數（Story Points）

> 由 spex-write-spec Phase 5.5 產出。採 MVP 複雜度單軸 Fibonacci `1 / 2 / 3 / 5 / 8 / 13 / 20`；
> 只衡量 MVP 實作複雜度，排除商業因素（失敗成本 / 風險 / 可逆性 / 優先級）；單卡上限 13（20 僅給 rollup 父卡）。
> 估點僅供規劃與 token 成本估算，**不影響 selfcheck 的 PASS/FAIL 判定**。

- 點數：<1 / 2 / 3 / 5 / 8 / 13>
- 維度理由：實作面 <…> / 狀態與契約 <…> / 整合面 <…> / 驗證工作量 <…>
- 拆卡判定：<若 ≥13 說明為何仍可單卡；若曾估 ≥20 列出拆卡方案；否則填「不需拆卡」>

## 參考資料

- <附件 / Figma / 相關 work item；無則填「無」>
```

## 品質檢核清單（write-spec Phase 5 / plan 輸入檢核共用）

- [ ] 必填章節齊全（使用者角色 / Why / In Scope / Out of Scope / AC / 邊界條件 / 列舉完整性清單 / 驗收場景）
- [ ] 每條 AC 二元可判定，無模糊詞，含格式或數值條件
- [ ] 每條 AC 可對應至少一種驗證方式（測試 / 指令 / 可觀察行為）
- [ ] 涉及「一組項目」的需求有完整成員列舉，未列舉成員已明示為範圍外
- [ ] 邊界條件四維度（空值 / 格式 / 上限 / 錯誤路徑）皆有交代或標「不適用」
- [ ] Out of Scope 非空（至少一條，防功能延伸）
- [ ] 預估開發點數已填（1–13），含四維度理由與拆卡判定
- [ ] 缺陷類需求另含：重現步驟、影響範圍、修復完成定義
