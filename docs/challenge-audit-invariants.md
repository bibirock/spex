# challenge-audit 不變式的由來（維護者文件）

> **本檔只在本 repo，不隨 `spex init` 安裝到使用者專案**（不在 `assets/` 底下）。
>
> `assets/reference/spex/scripts/challenge-audit.py` 依移植規範**清空了全部註解**。那些註解原本記載
> 「每條不變式是被什麼實戰失敗逼出來的」——沒有它們，後人很容易把 S0–S8 當成冗餘防禦而簡化掉。
> 本檔就是那份記憶。**修改該腳本前先讀本檔**；任何邏輯調整都要有新的實證理由，並補一列在下方。

---

## 為什麼章不可偽造

不是因為演算法強，而是因為**章的每個組成部分都不在執行模型的控制範圍內**：

| 元件 | 誰產生 | 執行者能否偽造 |
|---|---|---|
| 章號 | harness 生成的 `tool_use_id` / `agentId` | 不能（模型無法鑄造事件 id） |
| 章面 | 子代理輸出的末行標記，落在 `tool_result` / 子代理事件內 | 不能（主 agent 的文字進不了子代理事件） |
| 載體 | 事件流，位於 repo 之外 | 沙盒：物理寫不到；Claude Code：PreToolUse 硬閘擋改寫 |
| 內容綁定 | 章面 sha256 鎖定受審草稿 | 不能（改內容 → 雜湊不符） |

拿掉其中任何一項，「章」就退化成一句可以直接打出來的 `PASS`。

## 逐條不變式與其由來

| 代號 | 檢核 | 沒有它會發生什麼（實證失敗樣態） |
|---|---|---|
| **S0** | 首次 challenger 派發前，流中須有載入 `spex-challenge` 的事件 | 執行者「憑記憶」土製一個詰問流程——沒有 C1–C6 判準、沒有輪次硬上限、也不會蓋章，看起來有詰問實際上什麼都沒驗。腳本另有降級路徑：若全部派發都是真 challenger（有章面且實查 ≥8 次），降為警告而非 blocking，因為那是程序偏離而非造假 |
| **S1** | 宣稱必須引章號，且該章號存在、屬 challenger、完成於宣稱之前 | 「口頭 PASS」直接放行。這條是最基本的存在性檢查 |
| **S2** | 章面須為結構化 PASS；另查該卡該 stage 的最新章是否收斂到 PASS | 只驗「被引用的章」會留一個洞：拿一枚 FAIL 或未收斂的結果，用散文寫「✅ 通過」交棒。S2-收斂把尾端 verdict≠PASS 的整條流 block 掉。與 S4 同樣依 `(stage, card)` 分組，某卡的 FAIL 不會讓已收斂的別卡被連坐 |
| **S3** | 章面 round 與宣稱輪次相符且不超限 | 超限後續跑換到的 PASS 等於繞過「重做上限」，把該升級人工的案子硬推過去 |
| **S4** | 同一張卡、同 stage 的章數不超過上限 | 同上，從章的數量側再擋一次（宣稱可以少寫、章擋不掉）。分組鍵是 `(stage, card)`：章面的 `card=` 欄位讓批次跑多卡時各卡輪次互不累加——只依 stage 分組的話，4 張卡各自首輪就 PASS 也會湊滿上限被誤擋。舊事件流的章沒有 `card`，一律落在同一組，行為與加欄位前相同 |
| **S5** | 章面 sha256 與留言本體綁定（去除宣稱行後正規化） | 最常見的真實失敗：**蓋章後又潤飾留言**（縮寫、刪注記、改措辭），或圍欄放的是完整產物而留言另寫摘要。章綁不到最終內容 = 沒驗過那份內容。也順帶防重放（舊章蓋新內容） |
| **S6** | 一章一用 | 同一枚章支持兩個不同宣稱＝一次詰問當兩次用。註：被 S5 駁回後逐字重發屬合法重試，不消耗章 |
| **S7** | Verify 留言須引 verifier 章且 verdict=PASS | selfcheck 的獨立驗收同樣需要不可偽造的憑證，否則「獨立驗收」只是一段文字 |
| **S5-verify** | 驗收章的 sha256 綁定 verifier 報告的 `<!-- verify-report:start/end -->` 區塊，Verify 留言須逐字內嵌（另受 S8 保護） | 只驗「有跑過 verifier 且它整體說 PASS」會留一個洞：留言裡的 AC 對照表與防錯檢核結果不受章約束，編排者可以把驗證者判 FAIL 的 AC 改寫成 PASS、刪掉缺口層級，章照樣對得上。綁定範圍刻意不是整份留言——「章戳驗證」節記的是本次稽核自己的結果（雞生蛋），「確定性檢查」節是派發前就已知的事實 |
| **S8** | 章面含 sha256 時，子代理軌跡內須有真實雜湊計算的工具呼叫 | 曾發生子代理**憑空編造** sha256（沒跑任何計算就寫上去）。這種章一定過不了 S5，但代價是燒掉整輪才診斷出根因；S8 在章面產生當下就攔截 |
| **I3** | challenger / verifier 一律同步派發 | 非同步派發後，執行者在拿到真實回傳前就自行推測 verdict 續行＝造假 |

## 判準邊界（為什麼詰問會空轉，以及怎麼防）

移植時一併保留的幾條「防空轉」設計，全部來自真實的輪次燒穿：

- **階段判準邊界**：`task` 接點不得以「測試檔還不存在」「程式碼還沒寫」判 FAIL——那是 implement 的判準。曾有 challenger 反覆以下游判準審上游產出，把拆卡卡死。
- **行號誤差 ≤2 行不算假證據**：以「檔案＋符號＋語義」三者為準。曾有連續三輪 FAIL 全燒在「收尾括號要不要計進行號區間」，零品質增益。
- **判準穩定**：round ≥2 新增的 blocking FAIL 必須解釋「為何前輪沒發現」，否則降為 non-blocking。防止每輪換靶，讓實作方永遠過不了。
- **點名即全類別掃描**：發現一個缺失就要當輪掃完同類全部實例。分批揭露（擠牙膏）會用光輪次上限。
- **聚焦裁決**：唯一 blocking 類別是結構性缺漏、假綠、偷懶縮水、型別逃生口、假證據、上游矛盾。措辭／命名／格式微差一律 non-blocking——判不準時用「把實作換成空殼會不會照樣綠」當標準。

## 移植時對原型做的唯二調整

1. **品牌字串**：`[SpecTools]` → `[Spex]`、`spec-tools-challenge` → `spex-challenge`。
2. **`_resolve_max_rounds` 的搜尋路徑**：原型的腳本住在 `<repo>/sandbox/`，只需往上一層找 `.claude/rules/`。spex 把它安裝在 `.claude/reference/spex/scripts/`，且三個 agent 的規則目錄不同（`.claude` / `.spex` / `.codex`），故改為在多個 base 下逐一嘗試三種目錄。**沒改到的話**，Codex / Copilot 專案會靜默 fallback 到預設上限 5，與規則檔宣告的 3 不符。

除此之外邏輯逐字保留。回歸方式見下。

## 回歸驗證方式

移植與任何後續修改都用同一招：拿真實的歷史事件流跑，比對輸出是否逐字相同。

```bash
# 1) 準備一份把品牌字串改回原型的副本（隔離「品牌差異」與「邏輯差異」）
sed -e 's/\[Spex\\]/[SpecTools\\]/g' -e 's/spex-challenge/spec-tools-challenge/g' \
  assets/reference/spex/scripts/challenge-audit.py > /tmp/port-legacybrand.py

# 2) 對每一份歷史影子流，跑原型與移植版，比對 stdout、exit code 與 audit JSON
CHALLENGE_MAX_ROUNDS=3 python3 <原型>/sandbox/challenge-audit.py <流> 
CHALLENGE_MAX_ROUNDS=3 python3 /tmp/port-legacybrand.py <流>
```

移植當下的結果：37 份歷史影子流，stdout / exit code / JSON 報告**全數逐字相同**。

另有偽造注入測試（每次改動都應重跑）：

| 注入 | 期望 |
|---|---|
| 章面 sha256 改一個字元 | S5 內容綁定不符 |
| 宣稱引用不存在的章號 | S1 章號不存在 |
| 刪掉子代理的雜湊計算工具呼叫 | S8 疑似編造章面 |

Claude Code 平面另有合成 fixture（主 transcript ＋ `subagents/agent-<id>.jsonl` ＋ meta），驗證
`transcript-to-stream.mjs` → `challenge-audit.py` 這條路徑同樣能抓到上述三種偽造。
